# Memora 项目非安全审计与整改报告

> 审计范围：除「安全」外的所有方面（性能、流式体验、提示词质量、嵌入/重排/检索效果、交互可用性）。
> 目标读者：可直接动手改代码的开发者（含弱模型）。每条问题都给出「现象 → 根因（文件:行号）→ 详细解决方案 → 等级/难度/阶段」，并附可照抄的代码片段。
> 级别定义：**P0** 立即修（正确性/重大体验）· **P1** 高优先（明显影响使用）· **P2** 中优先（质量提升）· **P3** 低优先（优化）。
> 难度定义：**低**（改一个函数/常量）· **中**（改一个模块 + 联调）· **高**（跨模块设计调整）。

## 1. LLM 对话性能差 / 时间长

### A1 首字延迟高：检索 + 重排在流式开始前串行阻塞
- **现象**：点击发送后，前端长时间只显示等待光标，几秒后才开始流式出字。
- **根因**：`internal/qa/qa.go` 的 `Execute()` 先执行 `buildContext()`（第 229 行），其中包含 **嵌入查询 + 向量检索 + 批量取 chunk + 批量取文件 + 重排（最多 100 个候选）+ topK**，全部**同步完成后**才调用 `generateAnswer()` → `ChatStream()`。全局模式下重排 100 个候选 = 4 次 HTTP 往返（每批 32）。这段时间用户什么都看不到。
- **详细解决方案**（分两步，难度中）：
  1. **缩小重排输入规模**（配合 D2）：全局模式 `VectorsSearch(queryVec, 100)` 改为先向量召回 `top-40`，再对 40 个候选去重后重排。将重排 HTTP 往返从 4 次降到 2 次以内。
  2. **检索阶段向前端发「生成中」状态**（配合 B4）：在 `buildContext` 开始/结束时 `m.events.Notify("qa_ready", ...)` 或新增一个 `qa:thinking` 事件，让前端显示「正在检索文档…」，把「无响应」变成「有反馈」。
  3. **小文件直发已存在**（`fullTextDirectLimit=6000`），确认默认 chunk 文件小文件走的是直发、无检索延迟；对大文件才走检索。
- **代码定位**：`internal/qa/qa.go:229`（buildContext 调用）、`:591`（top-100）、`:627`（全量重排）。

### A2 无多轮对话历史，追问失效且每次重复检索
- **现象**：多轮追问（"那第二个呢？"）模型完全不知道上文，答非所问；且每一轮都重新嵌入 + 重排，重复开销。
- **根因**：`buildContext()` 只拼「当前问题 + 检索片段」，从不读取会话历史（`IStorage` 里有 `QAMessagesBySession`，但 QA 流程没用）。系统提示词也没有「根据对话历史回答」的约定。
- **详细解决方案**（难度中）：
  1. 在 `buildContext` 开头，若 `req.SessionID != 0`，调用 `m.storage.QAMessagesBySession(req.SessionID)`，取**最近 N 轮**（建议 N=4，即最近 8 条消息）拼进 userPrompt 顶部，格式：
     ```
     对话历史：
     用户：xxx
     助手：xxx
     ```
  2. 对历史做**字符上限**（如 2000 字），超出截断最旧的。
  3. 系统提示词补充一句：「以上是历史对话，请结合历史回答当前问题」（见 C2）。
  4. 可选优化：同会话、同 `Mode` 且 `FileID` 相同时，缓存上一次 `buildContext` 结果，追问时不重复检索（难度高，放阶段三）。
- **代码定位**：`internal/qa/qa.go:490`（buildContext）、`:32`（IStorage 已有 QAMessagesBySession）。

### A3 上下文按字符裁剪过宽，token 过多拖慢模型
- **现象**：默认 `qa.maxContextChars = 30000`，加上 top-8 每块 2000 字，单次提问上下文可达数万字符 ≈ 上万 token，首 token 与总时长都变慢、成本高。
- **根因**：`internal/config/config.go:131` 默认 30000；`buildContext` 用 `utf8.RuneCountInString` 累计裁剪（`:573`、`:636`），按「字符」而非「token」估算，且块数取 8 偏多。
- **详细解决方案**（难度低）：
  1. 默认 `MaxContextChars` 从 30000 降到 **8000**（中文约 4000~6000 token，足够回答绝大多数文档问题）。
  2. top-K 从 8 降到 **5**（`internal/qa/qa.go:571`、`:634`）。
  3. 裁剪上限取 `min(maxContextChars, 模型上下文的安全比例)`；若想更准，加一个 `estimateTokens(s) = runes/2`（中文）或 `runes/4`（英文）的粗估函数替代纯字符累计（难度低）。
- **代码定位**：`internal/config/config.go:131`、`internal/qa/qa.go:571/634`。

### A4 聊天/嵌入/重排共用全局限频，重建索引时拖慢对话
- **现象**：全量重建索引（嵌入数千 chunk）时，问 AI 明显变慢。
- **根因**：`internal/llm/llm.go:27-31` 用**单个 `sync.Mutex` + 单一 `rateLimit=50ms`（20 rps）**，`retry.go:12` 的 `rateLimitWait()` 对**聊天、嵌入、重排所有请求**统一限频并持锁。重建索引时 `Embed()` 成百上千次调用持续占用这个锁与限频窗口，聊天流式建连（`llm.go:232` 也调 `rateLimitWait`）被排在嵌入请求之后。
- **详细解决方案**（难度中）：
  1. 把限频器**按服务拆分**：`chatLimiter` / `embedLimiter` / `rerankLimiter` 三个独立 `rateLimiter`（各自 mutex + lastReqTime），互不阻塞。
  2. 嵌入/重排提高限频上限（如 100ms→10 rps 或直接移除，多数端点对批量嵌入限频宽松），聊天保持保守。
  3. 具体做法：新建 `rateLimiter` 结构体，`Module` 持有三个；`Chat/ChatStream` 用 chat，`Embed` 用 embed，`Rerank` 用 rerank。`retry`/`doRequest` 增加入参 `lim *rateLimiter` 或作为方法。
- **代码定位**：`internal/llm/llm.go:27-45`、`retry.go:12-21`、`llm.go:232`、`embed.go:57`、`rerank.go:57`。

### A5 流式为空时走非流式重试，加剧「慢」体感
- **现象**：部分端点流式解析为空时，后端静默改用**非流式**整体重试（等完整回答，最长 60s），前端长时间无字输出。
- **根因**：`internal/qa/qa.go:351-372` 空流兜底直接 `m.llm.Chat(...)`（非流式，无增量）。
- **详细解决方案**（难度中）：
  1. 优先**修好流式解析**（见第 2 节），减少触发兜底的概率。
  2. 兜底改为「先提示 + 非流式」，即向 sink 发一条提示块（如 `（流式不可用，正在等待完整回答…）`），让用户知道在等待。
  3. 给非流式重试也加**可取消**（当前重试前已检查取消，重试中不可打断，可接受）。
- **代码定位**：`internal/qa/qa.go:348-373`。

### A6 自动打标在索引流程串行调用 LLM
- **现象**：重建索引时，每个文件都额外做一次 LLM 打标（`ChatJSON`），文件多时索引完成时间被 LLM 往返拉长，且占用限频（与 A4 叠加）。
- **根因**：`internal/tag/tag.go:103-118` 在 `ProcessFile` 中对每个文件串行调用 LLM。
- **详细解决方案**（难度低）：
  1. 打标做成**可配置开关**（默认关或仅增量开启），或在任务队列中把 `tag` 任务与 `reindex` 解耦、异步执行。
  2. 最简单：在 `ProcessFile` 里把打标放入独立的 goroutine（带并发上限），不阻塞索引主流程。
- **代码定位**：`internal/tag/tag.go:74-190`。

## 2. 流式响应差

### B1 前端每次 flush 全量 Markdown 重渲染（最主要卡顿源）
- **现象**：流式回答时字是一坨一坨跳出来，页面卡顿，长回答尤其明显。
- **根因**：`frontend/src/components/ChatSurface.vue:213` 用 `v-html="renderMarkdown(msg.content)"`，而 `renderMarkdown`（`:49-84`）每次都对**整条消息**执行 `marked.parse` + 正则替换 + **`DOMPurify.sanitize`**。store 侧 `qa.ts:100-118` 每 **16ms 或每累积 8 字符** flush 一次，等于每秒几十次全量重渲染 + 净化，DOM 反复重建。
- **详细解决方案**（难度中，选其一）：
  1. **方案 A（推荐，改动小）**：流式进行中（`sending && 该消息是最后一条 assistant`）用**纯文本 `<pre>`/`<div>` 直接渲染 `msg.content`**（不做 markdown），等流结束再切换为 markdown 渲染一次。这样流式中零解析开销，结束后一次性渲染。
  2. **方案 B（更精细）**：记忆化——只对「新增的尾部 delta」渲染，已渲染前缀缓存为 HTML 字符串；DOMPurify 只在**完成后**净化一次，流式中用 `textContent` 追加。
  3. 配合调低 flush 频率：`qa.ts` 的 `16ms` 改为 `50ms`、`8 字符` 改为 `24 字符`，减少触发次数。
- **代码定位**：`ChatSurface.vue:49-84、213`、`stores/qa.ts:100-118、168-172`。

### B2 每个 chunk 走 Wails 全局事件广播，开销大
- **现象**：高频小 chunk（每 1~2 字符）逐个通过事件总线，前端回调密集、CPU 占用高。
- **根因**：`internal/assembler/services.go:632-634` 对每个 chunk 调 `emit(prefixChunk, chunk)`；前端 `client.ts:265-269` 每个 chunk 一次 `Events.On` 回调 + JSON 反序列化。
- **详细解决方案**（难度中）：
  1. 后端聚合：用 `time.Ticker`（如 30ms）或字符缓冲（累积 ≥16 字符）把多个小 chunk 合并成一次 `emit`，减少事件次数。
  2. 前端侧不再为每个 chunk 做额外处理（当前已合并到 store 的 `pending`，事件层也可配合）。
- **代码定位**：`internal/assembler/services.go:632-634`、`frontend/src/api/client.ts:265-269`。

### B3 `idleReadCloser` 每次 Read 新建 goroutine/timer
- **现象**：流式读取期间存在大量短生命周期 goroutine 与定时器分配（GC 压力）。
- **根因**：`internal/llm/stream_decode.go:98-125` 每次 `Read` 都 `go func()` + `make(chan)` + `time.NewTimer`。
- **详细解决方案**（难度低）：
  1. 用 `time.AfterFunc(idle, func(){ body.Close() })` + `defer timer.Stop()` 替代「goroutine + channel + select」，只有一个定时器回调，无每读 goroutine。
  2. 或在 `Read` 开始时 `Reset` 一个复用的 `time.Timer`。
- **代码定位**：`internal/llm/stream_decode.go:85-129`。

### B4 检索阶段前端无「检索中」反馈
- **现象**：发送后到首字前，界面只有光标，用户以为卡死。
- **根因**：`buildContext` 阶段没有任何事件推给前端。
- **详细解决方案**（难度低）：
  1. 在 `Execute` 的 `buildContext` 前 `m.events.Notify("qa_thinking", {sessionId, stage:"retrieving"})`，结束后 `stage:"generating"`。
  2. 前端 `qa.ts` 监听（或在 `send` 里本地置一个 `thinking` 状态），在 assistant 气泡显示「正在检索文档…」→「正在生成…」。
- **代码定位**：`internal/qa/qa.go:211-229`、`frontend/src/stores/qa.ts`。

## 3. 提示词弱

### C1 `qa.systemPrompt` 配置项被硬编码覆盖（明确 bug）
- **现象**：用户在设置里改了系统提示词，但问答行为毫无变化。
- **根因**：`internal/config/config.go:71` 定义了 `QA.SystemPrompt` 字段并支持 Get/Set/Snapshot（`:351/521/590`），但 `internal/qa/qa.go:170` 用**包级常量** `const systemPrompt = "..."`，`New()`（`:185`）也不接收配置，导致配置项完全失效。
- **详细解决方案**（难度低）：
  1. 在 `Module` 增加 `systemPrompt string` 字段；`New(...)` 增加入参 `systemPrompt string`，为空时回退默认常量。
  2. 调用侧 `assembler` 装配时传入 `config.Get("qa.systemPrompt")` 的值。
  3. `generateAnswer` 里把 `systemPrompt` 常量替换为 `m.systemPrompt`（两处：`:308`、`:320`、`:358`）。
- **代码定位**：`internal/qa/qa.go:170/185/308/320/358`、`internal/config/config.go:71`。

### C2 问答提示词过弱
- **现象**：弱模型回答容易跑题、编造、引用格式乱、输出冗长。
- **根因**：`systemPrompt` 只有一句，无 few-shot、无「禁止编造」强化、无输出结构约束、无「不确定分级」。
- **详细解决方案**（难度低，直接替换常量，并与 C1 联动）：
  参考增强版（可直接用）：
  ```
  你是 Memora 文档问答助手。只能依据下方标注了 [文件=路径, 段落=序号] 的片段作答。
  规则：
  1. 回答必须引用来源，格式原样为 [文件=路径, 段落=序号]（例：[文件=预算表.xlsx, 段落=3]），不要用反引号或只写文件名。
  2. 若片段能回答：先用一句话直接给出结论，再分点说明，用 Markdown（# 标题、- 列表、**加粗**）。
  3. 若片段信息不足：先说明"根据现有文档，只能确定以下内容……"，再列出已确认部分；完全无关则只回答"根据现有文档，未找到相关信息"。
  4. 严禁编造片段中不存在的数据、数字或结论；不要加开场白和结束语；回答尽量简洁。
  ```
  并让 `userPrompt` 结构化（`internal/qa/qa.go:261`）：
  ```
  相关文档片段：
  <contextStr>

  问题：<question>
  ```

### C3 打标提示词候选池小、无兜底校验
- **现象**：专业文档（财务/法务/技术）打标不准。
- **根因**：`internal/tag/tag.go:67-71` 候选池仅 20 个通用词；JSON 解析失败即静默跳过（`:118-123`）。
- **详细解决方案**（难度低）：
  1. 候选池加常见领域词（财务/法务/技术/人事等），或在提示词中允许「从文档标题/正文提取关键词作为新标签」。
  2. `ChatJSON` 失败时对输出做一次**宽松 JSON 清洗**（提取首个 `{...}` 再解析）再放弃。
- **代码定位**：`internal/tag/tag.go:67-71、103-123`。

### C4 提交/摘要提示词基础
- **现象**：提交备注风格不统一。
- **根因**：`internal/timeline/timeline.go:76/138` 提示词较简单。
- **详细解决方案**（难度低）：提交备注提示词加「可选前缀 feat/fix/docs/chore 等，中文场景可省略」，摘要加「突出行为变化而非文件罗列」。低优先。
- **代码定位**：`internal/timeline/timeline.go:76、138`。

## 4. 嵌入 / 重排效果差

### D1 重排对文档截断 800 字（重排效果差的头号原因）
- **现象**：关键信息在 chunk 后段时，重排排序不准确、检索不中。
- **根因**：`internal/llm/rerank.go:92` `maxRerankRunes = 800`，而默认 `chunkSize=2000`（`config.go:126`），长块 60% 内容被 `truncateRunes`（`:95-101`）截掉，交叉编码器只能看到开头。
- **详细解决方案**（难度低）：
  1. 把 `maxRerankRunes` 提到 **1800**（或与 `chunkSize` 对齐）；若担心请求体过大，配合 D2 减少候选数。
  2. 更优：对超长 chunk 取「首 60% + 尾 40%」拼接（保留开头结论与结尾结论，中间细节裁剪），示例：
     ```go
     func truncateRunesBalanced(s string, max int) string {
         r := []rune(s)
         if len(r) <= max { return s }
         head := max * 3 / 5
         tail := max - head
         return string(r[:head]) + "\n…[中略]…\n" + string(r[len(r)-tail:])
     }
     ```
- **代码定位**：`internal/llm/rerank.go:92-101、52-54`。

### D2 重排候选过多（100 个 chunk）
- **现象**：重排慢（4 次 HTTP）且无关 chunk 进入重排，交叉编码器对大量弱相关文档区分度下降。
- **根因**：`internal/qa/qa.go:591` 全局模式 `VectorsSearch(queryVec, 100)`，随后对全部 scoredChunks 重排（`:627`）。
- **详细解决方案**（难度中）：
  1. 向量召回从 100 降到 **40**；文件模式 `len(chunks)*2` 也设上限（如 40）。
  2. 重排前可先按余弦做一个粗排只取前 40（已有 topK 逻辑，可先 `topKByScore(scored, 40, cosine)` 再重排）。
- **代码定位**：`internal/qa/qa.go:591、627`。

### D3 重排分数直接替换余弦，无混合排序
- **现象**：重排端点质量一般或未配置时，排序不稳定。
- **根因**：`internal/qa/qa.go:564-568、627-631` 与 `search.go:157-161` 直接用重排分覆盖余弦分。
- **详细解决方案**（难度中）：
  1. 混合排序：`final = 0.5*normalize(cosine) + 0.5*normalize(rerank)`，其中 normalize 用 min-max 归一化。
  2. 重排失败时保持余弦顺序（当前已回退，保留）。
- **代码定位**：`internal/qa/qa.go:564-568`、`internal/search/search.go:157-161`。

### D4 嵌入查询指令固定单一，未按模型适配
- **现象**：对非 Qwen/bge 模型，固定指令前缀可能无效甚至有害。
- **根因**：`internal/llm/embed.go:96` `retrievalInstruction` 恒定。
- **详细解决方案**（难度低）：按配置的嵌入模型名（含 "qwen"/"bge"/"e5" 等）决定是否加前缀；E5 系列建议用 `query: ` 前缀。提供配置开关。
- **代码定位**：`internal/llm/embed.go:94-109`。

## 5. 嵌入搜索 / 模糊搜索搜不到

### E1 搜索页纯向量检索，无关键词/模糊兜底（核心缺陷）
- **现象**：按专有名词、文件编号、罕见词、文件名搜索时，搜索页「搜不到」；而 QA 对话里有标题兜底，搜索页没有。
- **根因**：`internal/search/search.go:66-92` 的 `Query()` 只有向量检索，无关键词/LIKE 兜底；`FilesFindByName`（`files_repo.go:169`）只在 QA 的 `buildContext` 兜底里用，搜索页没用。
- **详细解决方案**（难度中）：
  1. 在 `Query()` 里，向量检索之外**并行/串行**执行文件名关键词检索（`FilesFindByName` + `browser.SearchByName`），合并去重。
  2. 合并策略：向量结果 + 关键词结果，关键词命中的文件**加分或置顶**；向量无结果时直接返回关键词结果。
  3. 给 `IStorage` 增加一个 `FilesFindByName` 到 search 的接口（search 的 `IStorage` 目前没有该方法，需新增）。
- **代码定位**：`internal/search/search.go:66-92`、`internal/storage/files_repo.go:169`。

### E2 中文查询未预处理，噪声词拉低相似度
- **现象**：整句带语气词/疑问词的查询嵌入后，与文档片段相似度偏低。
- **根因**：`EmbedQuery` 直接嵌入原文（`embed.go:100`），搜索/问答未去除「请问、帮我、看看、呢、吗」等停用词/疑问词，未提取核心实体。
- **详细解决方案**（难度中）：
  1. 复用/强化 `qa.go:781` 的 `extractFilenameKeyword` 思路，做**查询清洗**：去疑问词、去停用词、提取引号内实体。
  2. 用清洗后的「核心查询」做嵌入，同时用「原查询」做重排（重排输入保持自然语言更佳）。
  3. 增加一个 `cleanQuery()` 帮助函数放到 `internal/llm` 或 `search`，供 search 与 qa 共用。
- **代码定位**：`internal/llm/embed.go:100`、`internal/qa/qa.go:781-807`。

### E3 余弦分数未归一化/无阈值，弱相关结果稀释
- **现象**：搜索结果前几页混入大量弱相关文件。
- **根因**：`index_repo.go:428-455` 纯线性扫描余弦，`search.go`/`qa.go` 直接按原始余弦排序，无归一化、无最低分阈值。
- **详细解决方案**（难度低）：
  1. 对余弦结果做 min-max 归一化后再与关键词/重排混合。
  2. 增加**最小分数阈值**（如归一化后 <0.3 且非关键词命中的丢弃），避免弱相关稀释。
- **代码定位**：`internal/storage/index_repo.go:428`、`internal/search/search.go:210-218`。

### E4 文件名搜索仅 `LIKE` 子串，无容错
- **现象**：文件名记错一个字/顺序就搜不到。
- **根因**：`files_repo.go:169` 用 `LIKE '%kw%'`，`browser.go:113` 用 `strings.Contains`，均无编辑距离/子序列/拼音容错。
- **详细解决方案**（难度中，放阶段三）：
  1. 引入轻量子序列匹配：把查询拆成单字，要求文件名按序包含（`isSubsequence`），比 `LIKE` 更宽松。
  2. 或对「无结果」时降级为编辑距离 ≤2 的匹配。
  3. 可选：SQLite FTS5 建文件名全文索引（改动大，属可选增强）。
- **代码定位**：`internal/storage/files_repo.go:169`、`internal/browser/browser.go:106-155`。

## 6. 打开文件夹必须借助 PowerShell

### F1 选文件夹依赖 PowerShell（跨平台/健壮性问题）
- **现象**：点「选择文件夹」依赖 `powershell.exe`，未装 PowerShell 或被杀软拦截时无法选目录；非 Windows 直接报「不支持」；中文路径靠输出编码 hack。
- **根因**：`internal/browser/browser.go:191-228` `PickDirectory`/`pickWindowsDir` 用 `exec.Command("powershell.exe", "-STA", ...)` + `System.Windows.Forms.FolderBrowserDialog`。
- **详细解决方案**（难度中，推荐用 Wails 原生对话框，已确认项目依赖 Wails v3.0.0-beta.8 提供该能力）：
  1. 把 `PickDirectory` 改为调用 Wails 原生目录选择器（Windows 走 COM `IFileDialog`，无需 PowerShell；macOS 走 NSOpenPanel；Linux 走 GTK）：
     ```go
     import "github.com/wailsapp/wails/v3/pkg/application"

     func PickDirectory(initial string) (string, error) {
         app := application.Get()
         if app == nil {
             return "", fmt.Errorf("[browser] 应用未就绪")
         }
         dlg := app.Dialog.OpenFile().
             SetTitle("选择目录").
             CanChooseDirectories(true).
             CanChooseFiles(false)
         if initial != "" {
             dlg = dlg.SetDirectory(initial)
         }
         path, err := dlg.PromptForSingleSelection()
         if err != nil {
             return "", fmt.Errorf("[browser] 选择目录失败: %w", err)
         }
         return path, nil // 用户取消时 path 为空串
     }
     ```
  2. 由于 `application.Get().Dialog` 需要应用已启动，`services.go:480-502` 的 `PickDir` 里保留空串=取消的语义；可去掉 3 分钟超时包装（原生对话框自己管理生命周期，或保留超时兜底）。
  3. 注意：`browser.go` 不再需要 `syscall` 与 `os/exec` 的 PowerShell 分支；`OpenFile` 保留（用 `rundll32/open/xdg-open` 打开文件是合理的，可继续）。
  4. 若坚持不依赖 Wails 对话框，可选纯 Go 原生库 `github.com/sqweek/dialog`（Windows COM，无 PowerShell），但既然项目已用 Wails，优先 Wails 原生。
- **代码定位**：`internal/browser/browser.go:191-228`、`internal/assembler/services.go:480-502`。
- **配套小修**：`useSettings.ts` 里「选 Python 解释器」用目录选择器再拼 `python.exe` 很别扭（`useSettings.ts:243-260`），应改用**文件选择**对话框（`OpenFile()` + `CanChooseFiles(true)`），选 `.exe` 直接得路径。

## 7. 其他非安全问题（顺带发现，低优先）

1. **`extract.go` 提取依赖 Python + MarkItDown 子进程**：对超大文件/批量重建，逐个启动子进程（60s 超时）较慢。可考虑并发提取（有 worker 池上限）。缓存已有 SHA256 命中，属于正常。低优先。
2. **`FilesUpsert` 每次先 `FilesFindByRelPath` 再写再回查**，一次 upsert 三次 DB 往返，全量重建时文件多会放大。可合并为单条 UPSERT + RETURNING（SQLite 支持）。中优先、难度中。
3. **`VectorsSearch` 每次 `make([]vectorEntry, len(m.vectorIndex))` + `copy` 全量复制**（`index_repo.go:434-435`），向量量大时每次查询都全量拷贝。可加读快照/分段。低优先。
4. **标签过滤 OR 语义**：`search.go:196-207` 多标签是「任一命中」，若用户预期「且」需明确。低优先。
